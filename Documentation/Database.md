# Database.md

**Engine:** SQLite, single file `driverisk.db`
**ORM:** SQLAlchemy
**Location:** `backend/driverisk.db`
**Readers:** FastAPI backend (read/write), Streamlit dashboard (read-only, direct file access)

The design document locks **five tables**. No sixth table is introduced. Column definitions were not specified in Section 1 (Section 21 is unwritten), so all columns below are `[INFERRED]` and need your sign-off before the models are written.

---

## Table count and ownership

| # | Table | Written by | Read by |
|---|---|---|---|
| 1 | `trips` | Backend on trip creation | App, Dashboard |
| 2 | `raw_sensor_data` | Backend on upload | Processing layer |
| 3 | `features` | Processing layer | ML layer, Dashboard |
| 4 | `predictions` | ML layer | App, Dashboard |
| 5 | `shap_explanations` | Explainability layer | App, Dashboard |

---

## 1. `trips`

One row per driving session. `trip_id` is generated by the Android app (matches `trip.md`), so it is a client-supplied string primary key rather than an autoincrement integer. This lets the app create the trip locally in Room before it has network access.

| Column | Type | Constraints | Notes |
|---|---|---|---|
| `trip_id` | TEXT | PK | Client-generated, e.g. `trip_001` |
| `user_id` | TEXT | NOT NULL, INDEX | e.g. `driver_001` |
| `device_model` | TEXT | NULL | e.g. `Samsung S23 FE` |
| `start_time` | TEXT | NOT NULL | ISO 8601 UTC |
| `end_time` | TEXT | NULL | ISO 8601 UTC, set on first upload |
| `duration_s` | REAL | NULL | Computed at processing time |
| `distance_km` | REAL | NULL | Computed from GPS path (haversine) |
| `sample_count` | INTEGER | DEFAULT 0 | Running count of uploaded rows |
| `status` | TEXT | NOT NULL, DEFAULT `CREATED` | See status enum below |
| `created_at` | TEXT | NOT NULL | Server timestamp |
| `processed_at` | TEXT | NULL | Server timestamp |

**Status enum (locked):** `CREATED` → `UPLOADING` → `UPLOADED` → `PROCESSING` → `PROCESSED`, plus terminal `FAILED`.

The app's Room `upload_status_table` mirrors this so offline devices can resume.

## 2. `raw_sensor_data`

One row per sensor sample. Highest-volume table by far: 50 Hz for a 30-minute trip is roughly 90,000 rows.

| Column | Type | Constraints | Notes |
|---|---|---|---|
| `id` | INTEGER | PK AUTOINCREMENT | |
| `trip_id` | TEXT | FK → `trips.trip_id`, INDEX | ON DELETE CASCADE |
| `timestamp` | INTEGER | NOT NULL | Epoch milliseconds |
| `latitude` | REAL | NULL | GPS at 1 Hz, so null on most IMU rows |
| `longitude` | REAL | NULL | |
| `speed` | REAL | NULL | km/h |
| `accel_x` | REAL | NOT NULL | m/s² |
| `accel_y` | REAL | NOT NULL | m/s² |
| `accel_z` | REAL | NOT NULL | m/s², includes gravity |
| `gyro_x` | REAL | NOT NULL | rad/s |
| `gyro_y` | REAL | NOT NULL | rad/s |
| `gyro_z` | REAL | NOT NULL | rad/s |

**Index:** `(trip_id, timestamp)` — every processing read is ordered by this pair.

GPS columns are nullable because the IMU runs at 50 Hz and GPS at 1 Hz. The preprocessing step forward-fills GPS across the intervening IMU samples.

## 3. `features`

One row per sliding window (5 s, 50% overlap). This is the model's actual input table.

### Identity and geometry

| Column | Type | Notes |
|---|---|---|
| `id` | INTEGER | PK AUTOINCREMENT |
| `trip_id` | TEXT | FK → `trips.trip_id`, INDEX |
| `window_index` | INTEGER | 0-based, ordered |
| `window_start_ts` | INTEGER | Epoch ms |
| `window_end_ts` | INTEGER | Epoch ms |
| `center_lat` | REAL | Window centroid — used to colour the risk map |
| `center_lon` | REAL | |

### The 24 model features

Speed: `speed_mean`, `speed_max`, `speed_std`
Acceleration: `accel_mag_mean`, `accel_mag_std`, `accel_mag_max`, `accel_long_mean`, `accel_long_min`, `accel_long_max`, `accel_lat_max`
Jerk: `jerk_mean`, `jerk_max`
Gyroscope: `gyro_mag_mean`, `gyro_mag_std`, `gyro_z_max`
Events: `harsh_brake_count`, `harsh_accel_count`, `harsh_corner_count`, `overspeed_count`
Road geometry: `heading_change_total`, `bearing_std`, `curvature_mean`
★ Novelty: `curve_density`
Interaction: `curve_density_x_speed_mean`

All REAL except the four `*_count` columns, which are INTEGER.

> `feature_list.json` in `backend/ml_model/` is the **authoritative** definition of which of these columns are fed to the model and in what order. If this table and that file ever disagree, the file wins and the mismatch is a bug.

### Prediction result (written by the ML layer)

| Column | Type | Notes |
|---|---|---|
| `predicted_label` | TEXT | `LOW` / `MEDIUM` / `HIGH`, NULL until prediction |
| `predicted_confidence` | REAL | Max class probability |

**Why here and not in a sixth table:** the risk map needs a label per window, and the design document locks the table count at five. Storing the window label on the row that produced it keeps that constraint and avoids a join on the largest analytical table. `[INFERRED]`

**Unique constraint:** `(trip_id, window_index)`.

## 4. `predictions`

One row per trip. This is what the Result screen reads.

| Column | Type | Notes |
|---|---|---|
| `id` | INTEGER | PK AUTOINCREMENT |
| `trip_id` | TEXT | FK → `trips.trip_id`, **UNIQUE** |
| `trip_score` | REAL | 0–100 |
| `risk_level` | TEXT | `LOW` / `MEDIUM` / `HIGH` |
| `window_count` | INTEGER | Total windows scored |
| `pct_low` | REAL | % of windows labelled LOW |
| `pct_medium` | REAL | % labelled MEDIUM |
| `pct_high` | REAL | % labelled HIGH |
| `weight_w1` | REAL | Weight applied to `pct_high` |
| `weight_w2` | REAL | Weight applied to `pct_medium` |
| `harsh_braking_count` | INTEGER | Trip totals for the event list |
| `harsh_acceleration_count` | INTEGER | |
| `harsh_cornering_count` | INTEGER | |
| `overspeeding_count` | INTEGER | |
| `curve_density_trip` | REAL | Curves per km for the whole trip |
| `model_name` | TEXT | `RandomForest` or `XGBoost` |
| `model_version` | TEXT | Training run identifier |
| `created_at` | TEXT | |

Storing `weight_w1` / `weight_w2` per row means any historical trip score stays reproducible even after the weights are tuned. Storing `model_name` means the dashboard can state which model actually produced each result.

**Score formula (locked):**
```
trip_score = 100 − ( w1 · pct_high + w2 · pct_medium )
risk_level = LOW if ≥ 70, MEDIUM if 40–69, HIGH if < 40
```

## 5. `shap_explanations`

One row per contributing feature per trip — 3 to 5 rows for a normal trip.

| Column | Type | Notes |
|---|---|---|
| `id` | INTEGER | PK AUTOINCREMENT |
| `trip_id` | TEXT | FK → `trips.trip_id`, INDEX |
| `rank` | INTEGER | 1 = strongest contributor |
| `feature_name` | TEXT | Must exist in `feature_list.json` |
| `shap_value` | REAL | Signed mean SHAP value across windows |
| `feature_value` | REAL | Trip-level value of that feature, for context |
| `direction` | TEXT | `INCREASES_RISK` / `DECREASES_RISK` |
| `reason_text` | TEXT | Plain-language sentence shown in the app |

**Unique constraint:** `(trip_id, rank)`.

Global SHAP importance for the dashboard is **not** stored here. It is a training-time artifact and belongs with the model files.

```
trips (1) ──< raw_sensor_data      ON DELETE CASCADE
      (1) ──< features             ON DELETE CASCADE
      (1) ──1 predictions          ON DELETE CASCADE
      (1) ──< shap_explanations    ON DELETE CASCADE
```

## Operational notes

- Enable `PRAGMA foreign_keys = ON` per connection — SQLite ignores FK constraints otherwise.
- Enable WAL mode. Streamlit reads the file while FastAPI writes to it; without WAL you will hit `database is locked`.
- Batch-insert `raw_sensor_data` with `bulk_insert_mappings`. Row-by-row ORM inserts for 500-row batches at 90k rows per trip are the single most likely performance failure in this build.
- Reprocessing a trip must delete its existing `features`, `predictions` and `shap_explanations` rows first, so `POST /process` stays idempotent.
- `raw_sensor_data` is never read by the app or dashboard, only by the processing layer.
